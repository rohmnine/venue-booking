# 推送通道配置指南（怎么让提醒真的送到你手上）

监测到空位只是第一步，**提醒必须真的送达**。本文覆盖各渠道的开通步骤、配置写法、验证方法与排错。

---

## 零、先选渠道

| 渠道 | `notify.type` | 适合谁 | 门槛 | 限额 |
| --- | --- | --- | --- | --- |
| **企业微信**群机器人 | `wecom` | 公司用企业微信 | 需企业微信账号 + **内部群** | 20 条/分钟 |
| **钉钉**群机器人 | `wecom` | 公司用钉钉 | 需钉钉账号 + 群 + **关键词** | 20 条/分钟 |
| **飞书**群机器人 | `feishu` | 公司用飞书 | 需飞书账号 + 群 + **安全设置** | 100 次/分钟 |
| **Server酱** | `serverchan` | **个人用户首选** | 只需微信扫码登录 | ⚠️ **5 条/天** |
| **PushPlus** | `pushplus` | 个人用户备选 | 只需微信扫码登录 | 有每日限额 |
| **Bark** | `bark` | iPhone 用户 | 装一个 App | 宽松 |

> **关键取舍**：企业微信/钉钉/飞书都要「**先有一个群**」，个人用户往往没有；
> 而 Server酱 微信扫码即用，但免费版**每天只有 5 条**。
>
> - 只要「能用、省事」→ **Server酱**（注意 5 条/天的额度，引擎已内置保护）
> - 要「长期稳定、不限量」→ **飞书**（100 次/分钟），代价是要建个群
> - 有 iPhone → **Bark** 也很干净

## 零·五、消息到底发到哪里？（一个常见误解）

很多人以为「提醒是发到我的电脑上，所以必须开着电脑、开着客户端」——**不是的**。
所有 webhook 类渠道（企业微信 / 钉钉 / 飞书）走的都是同一条路：

```
你的脚本 ──HTTP POST──> 厂商服务器（如 open.feishu.cn）
                            │
                            └─> 投递到「那个群」
                                   │
                                   ├─> 推送到你登录的**所有设备**
                                   │     PC 客户端 / 手机 App / 网页版
                                   └─> 消息**永久保存在群历史**里
```

由此推出几条实用结论：

| 问题 | 答案 |
| --- | --- |
| 电脑上的飞书客户端要开着吗？ | **不用**。消息早就到飞书服务器了 |
| 电脑关机了还能收到吗？ | **能**。手机照样收 |
| 手机会收到吗？ | **会**，只要手机登录的是同一个账号 |
| 手机当时没网 / 没开 App？ | 联网后仍能在群历史里看到，**消息不会丢** |
| 发消息的那台电脑要一直开着吗？ | **要**。它是「发起方」，它不跑就没人去查 |

> ⚠️ **发起方和接收方是两回事，别混**：
> - **发起方** = 跑监测脚本的那台机器（**必须开着**，否则没人去查接口）
> - **接收方** = 你的飞书账号（客户端开不开、关不关都无所谓）
>
> 另外，飞书群机器人**只能发到群、不能发私聊** —— 所以你必须**在那个群里**。
> 群是别人建的、你不在群里，就收不到。

**没收到提醒时的自查顺序**：

1. 你的账号在机器人所在的那个群里吗？
2. 手机飞书登录的是同一个账号吗？
3. 手机通知权限开了吗？系统有没有把它限制后台运行？
4. 那个群是不是设了**免打扰**（消息会到，但不响）？
5. 用 `notify-test` 发一条测试消息，确认通道本身是通的。

## 一、企业微信群机器人（详细）

### 步骤

1. 打开**企业微信**（手机端或 PC 端都行）。
2. 进入任意一个**群聊**（必须是**企业内部群**，见下方卡点①）。
3. 点右上角 **`…`** → **群机器人** → **添加机器人** → **新建**。
4. 给机器人起个名字（如「订场提醒」），点**添加**。
5. 复制弹出的 **Webhook 地址**，形如：

```
https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=693a91f6-7xxx-4bc4-97a0-0ec2sifa5aaa
```

### 常见卡点

| # | 现象 | 原因 |
| --- | --- | --- |
| ① | 群设置里**找不到「群机器人」** | 这个群是**外部群**（含微信用户/外部联系人）。机器人只在**企业内部群**可用，换一个纯同事群 |
| ② | 同上 | 企业管理员在后台**禁用了群机器人**功能，需找管理员开通 |
| ③ | 地址拿到但发送失败 | Webhook 地址**被重置过**（重新生成会失效旧地址），或**机器人已被移出群** |
| ④ | 群里能看到消息但格式乱 | 用错了 `notify.type`（比如把飞书地址填成 `wecom`），报文格式对不上 |

### 频率限制

企业微信群机器人限制 **每分钟 20 条**。本 skill 只在「有新空位」时推送，正常远低于这个量；
但如果你把轮询间隔压到 1 分钟、又恰好连续有新空位，可能触发限流。届时消息会发送失败，
`check` 的日志里会打印 `[notify] 推送失败`，但**不影响监测本身**。

### 填进配置

```json
"notify": {
  "type": "wecom",
  "webhook_url": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=693a91f6-...",
  "no_proxy": true
}
```

## 二、钉钉群机器人

步骤与企业微信类似：群设置 → **智能群助手** → 添加机器人 → **自定义**（通过 Webhook 接入）→ 复制地址。

> ⚠️ 钉钉的「自定义机器人」有一个**安全设置**，必须三选一：
> **加签 / 自定义关键词 / IP 白名单**。最省事的是**自定义关键词** ——
> 填一个必然会出现在消息里的词（比如场馆名），否则钉钉会拒收。

配置：`"type": "wecom"`（钉钉与企业微信的报文格式**完全一致**，可共用）。

## 三、飞书群机器人

### 步骤

1. 打开**飞书**，进入目标群聊。
2. 群设置 → **群机器人** → **添加机器人** → **自定义机器人**。
3. 起名（如「订场提醒」）→ 添加。
4. 配置**安全设置**（见下方，这一步不做会收不到消息）。
5. 复制 **Webhook 地址**，形如：

```
https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxxxxxxxxxxx
```

### ⚠️ 安全设置：必须三选一（最容易漏的一步）

飞书自定义机器人提供三种安全设置，**至少设一种**，否则任何人都能用这个地址往你群里发消息：

| 方式 | 说明 | 推荐度 |
| --- | --- | --- |
| **自定义关键词** | 只有**包含至少一个关键词**的消息才能发送成功 | ⭐ 最省事 |
| **IP 白名单** | 只有白名单内的 IP 能调用 | 本机公网 IP 会变，不实用 |
| **签名校验** | 请求必须带 `timestamp` + `sign` | 最安全 |

#### 用「自定义关键词」时要注意

关键词**只对 `text` / `title` 这类文本参数值生效**，且必须**原样出现**在消息文本里。

本 skill 发出的消息长这样（真实提醒）：

```
【xx市体育馆】有场放出了
📅 9/18（明天） 刚开放预订 · 新增 5 个空场
20:00-20:30 · 12号场
21:00-21:30 · 2号场
21:30-22:00 · 2号场、7号场、9号场

👉 去小程序订：#小程序://xx市体育馆/xxxxxxxxxxxxxxxx
```

所以关键词建议填 **`空场`** 或 **`有场`**，或者**你自己场馆名里的词** ——
前两个必然出现在正文里（「有场放出了」「新增 N 个空场」），后者必然出现在标题里。
填「订场」「提醒」之类的词有可能匹配不上。最多可设 10 个关键词，回车分隔。

> 校验失败时飞书返回 `{"code":19024,"msg":"Key Words Not Found"}`。

#### 文案为什么这么设计（改之前先看这里）

| 决定 | 原因 |
| --- | --- |
| **不放本地文件路径** | 旧版末尾跟一行 `详情：A:\...\outputs\xxx.md`。在手机上**完全没用** —— 点不开、看不懂，还暴露本机目录结构。已改成放**小程序链接**，收到就能直接去订 |
| **按时段归并** | 同一时段有多个场地时合成一行（`21:30-22:00 · 2号场、7号场、9号场`）。5 个空位从 5 行压到 3 行，扫一眼就够 |
| **直接写「时段 · 几号场」** | 内部 key 是 `2026-09-18\|20:00-20:30\|12`（`\|` 拼接便于快照比对），直接甩给用户会让人猜那个 `12` 是什么。展示时转成人读格式，**只在展示层转换，不动 key 本身**，所以不影响快照比对 |
| **日期带「今天/明天」** | 省得心算 |
| **单条最多 12 个时段** | 再多就把消息撑爆了。可用 `notify.max_slots_in_message` 调 |

仍想带本地路径（例如推给自己电脑上的脚本处理），把 `notify.include_report_path` 设为 `true`。

#### 只在「有新空位」时才推 —— 这是最容易误解的一点

**飞书安静 ≠ 没有空位。** 引擎只在**出现新空位**时推消息。某个空位昨天记录过了、今天还在，
不会再推一次，否则每个整点都会收到一条没有新信息的重复消息。

所以「一整天没消息」的正确含义是：**这段时间没有新场放出来**，不是「没有空位」。

实测踩过这个坑：用户看到 9/18 在小程序里明明有空场，却一整天没收到提醒，
以为程序坏了。其实那 5 个空场在 16:13 就已经推过一次了，后续运行比对下来「无新增」，按设计不推。

#### 每日摘要：解决「安静 vs 挂了」无法区分的问题

配一条摘要，每天固定时刻推「当前全部空场」：

```json
"notify": {
  "webhook_url": "...",
  "daily_digest_at": "10:35"
}
```

```
【xx市体育馆】每日摘要 · 当前 5 个空场
9/18（明天）　共 5 个空场
20:00-20:30 · 12号场
21:00-21:30 · 2号场
21:30-22:00 · 2号场、7号场、9号场

👉 去小程序订：#小程序://xx市体育馆/xxxxxxxxxxxxxxxx

（每日 10:35 推一条汇总；一旦出现新空位仍会立即提醒）
```

**时间语义是「过了点就补发」，不是「准点发」** —— 计划任务整点触发，10:35 那一刻没有进程在跑。
两道保障：

1. `watch` 在上午轮询窗口（到 10:30）结束后**顺延到 10:35** 补跑一次 → 正常情况下准时
2. 万一那次被中断（关机 / 强杀），下一个整点（11:00）的运行**兜底补发**

当天只发一次（记在 `state/<id>-digest.json`）。摘要时刻留空 = 不启用。

**摘要时刻怎么选？** 取决于它落在哪：

| 落在哪 | 送达方式 | 例子 |
| --- | --- | --- |
| **轮询窗口之内** | 轮询循环每 90 秒跑一次 check，到点自然发出 | 窗口 08:50–10:30，摘要定 `09:30` |
| **窗口结束后 45 分钟内** | `watch` 轮询结束（10:30）后**顺延到那个点**补跑一次 | 摘要定 `10:35` → 准时 |
| **更晚** | 等下一个整点运行**兜底补发**（会晚，但不丢） | 摘要定 `14:00` → 15:00 才发 |

推荐 **`10:35`**：上午放号窗口刚结束，此时摘要能看到「今天放了哪些号」的完整结果。

> 用 `status` 可以随时确认摘要状态：
> ```
> 每日摘要     : 今天已发（2026-09-17 17:05:19，定在 10:35）
> ```
> 若显示「⚠️ 已过 10:35 但今天还没发」，说明补发那次运行也没跑成，需要查调度。

#### 用「签名校验」时

把密钥填进配置，引擎会自动计算并带上 `timestamp` 和 `sign`：

```json
"notify": {
  "type": "feishu",
  "webhook_url": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx",
  "feishu_secret": "你的签名密钥"
}
```

### 配置

```json
"notify": {
  "type": "feishu",
  "webhook_url": "https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxxxxxxxxxxx"
}
```

> ⚠️ 飞书的报文格式与企业微信**不同**，`type` 必须写 `feishu`。
> 写错的表现是「HTTP 200 但收不到」。

### 频率限制

**单机器人 100 次/分钟、5 次/秒**，本项目用量远低于此，基本不受限。
飞书官方另有一条建议：**尽量避开 10:00、17:30 这类整点/半点发送**，
否则可能撞上 `11232` 限流错误。本 skill 的定时任务是整点触发的，
若偶尔推送失败可忽略（下轮会重试）；介意的话把自动化触发时间错开整点即可。

## 四、Server酱（个人用户最省事）

Server酱有**两个版本，SendKey 不通用、API 地址也不同**。选一个注册即可（也可以都注册，各有免费额度）：

| | Server酱 Turbo（SCT） | Server酱³（SC3） |
| --- | --- | --- |
| SendKey 格式 | 以 **`SCT`** 开头 | 以 **`sctp`** 开头，形如 `sctp{uid}t…` |
| 推送到 | **微信**（服务号） | **独立 App**（多设备，需先装 App） |
| 注册入口 | <https://sct.ftqq.com> | <https://sc3.ft07.com> |
| API 地址 | `https://sctapi.ftqq.com/<SendKey>.send` | `https://<uid>.push.ft07.com/send/<SendKey>.send` |
| 免费额度 | **每天 5 条** | 测试期免费 |

> 只想在**微信**里收通知 → 选 **Turbo**。
> 想要独立 App、AI 摘要、Tag 分组 → 选 **SC3**（但要先装 App，否则收不到）。

### Turbo 配置步骤

1. 打开 <https://sct.ftqq.com>，**微信扫码**登录（注册即为免费会员，每天 5 条）。
2. 进入「SendKey」页面，复制密钥（`SCT` 开头）。
3. **关注它提示的微信服务号**（不关注收不到消息）。

### 配置写法

**两种 SendKey 都可以只填密钥**，引擎会按前缀自动识别版本并补全地址：

```json
"notify": {
  "type": "serverchan",
  "webhook_url": "SCT123456xxxxxxxxxxxxxxxxx"
}
```

```json
"notify": {
  "type": "serverchan",
  "webhook_url": "sctp1234tXXXXXXXXXXXXXXXXXX"
}
```

也可以直接粘贴完整地址（从 SendKey 页面复制的 API URL 原样贴进来即可）。

### ⚠️ 免费版每天只有 5 条 —— 引擎已内置配额保护

Server酱 Turbo 免费会员**每天最多 5 条**，超出的请求会失败。
本 skill 已做防护：默认对 `serverchan` 渠道启用**每日 5 条上限**，
超出后跳过推送并在日志里明确说明（报告仍会正常落盘，不会丢数据）。

想调整上限：

```json
"notify": {
  "type": "serverchan",
  "webhook_url": "SCT...",
  "daily_limit": 5
}
```

> 实际用量很低：引擎只在「发现**新增**空位」时推送一次，同一批空位不会重复推。
> 但如果你把轮询间隔压到分钟级、又恰好连续有新空位释放，仍可能撞上限。
> **追求稳定的话，飞书群机器人（100 次/分钟）比 Server酱更耐打。**

### 验证 SendKey 是否可用（官方给的命令）

```bash
# Turbo
curl -X POST "https://sctapi.ftqq.com/你的SENDKEY.send" -d "title=测试" -d "desp=可用"

# SC3（把 <uid> 换成 sctp 和 t 之间的数字，如 sctp123tXXX → 123）
curl -X POST "https://<uid>.push.ft07.com/send/你的SENDKEY.send" -d "title=测试" -d "desp=可用"
```

返回 JSON 里 `code` 为 `0` 且收到消息，即为成功。

## 七、验证（必做）

配完**一定要验一次**，别等真放号了才发现推不出去。

验证要分两层。**只做第一层会留下一个致命盲区**：测试消息收到了，但真实报警永远不来 ——
因为 `notify-test` 是绕开触发逻辑直接发消息的，触发条件写错它照样 ✅。

### 第一层：验通道（消息能不能发出去）

```bash
python scripts/venue_monitor.py notify-test -v example-venue
```

正常输出：

```
渠道：feishu（飞书群机器人）
目标：https://open.feishu.cn/open-apis/bot/v2/hook/****
代理：绕过系统代理（直连）

✅ 测试消息已发送 —— 请检查对应 App / 群是否收到。
```

看到 `✅` 且手机/群里收到消息，第一层才算通。

### 第二层：验链路（比对出新空位时，会不会真的推）

手工制造一个「新增空位」，逼出真实的报警路径：

```bash
# 1. 备份快照（状态文件在 state/<venue-id>.json）
cp state/example-venue.json state/example-venue.json.bak

# 2. 从快照里删掉一条已有空位 —— 下一轮 check 就会把它当成「新增」
python -c "
import json,io
p='state/example-venue.json'
d=json.load(io.open(p,encoding='utf-8'))
print('移除:', d['available'].pop(0))
io.open(p,'w',encoding='utf-8').write(json.dumps(d,ensure_ascii=False,indent=2))
"

# 3. 跑一次 check，应看到 🆕 新增空余 + [notify] 已推送
python scripts/venue_monitor.py check -v example-venue

# 4. 清理备份（快照会被 check 自动写回真实值，无需手工还原）
rm -f state/example-venue.json.bak
```

看到 `🆕 新增空余 1 条` + `[notify] 已推送 ->`，且群里真收到消息 —— 整条链路才算通。

### ⚠️ HTTP 200 不等于推送成功

飞书 / 钉钉 / 企微都是「HTTP 200，结论在响应体里」。只看状态码会把失败当成功。
要确认就读响应体：

```
# 飞书成功长这样
{"StatusCode":0,"StatusMessage":"success","code":0,"data":{},"msg":"success"}
```

飞书签名算错的错误码是 **`19021 sign match fail`** —— 见到它说明 `feishu_secret` 填错，
或安全设置选的不是「签名校验」（三选一里选错了）。

## 八、排错表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 提示未配置 webhook | `notify.webhook_url` 为空 | 填上地址或密钥 |
| `❌ 推送失败`，连接超时 | 走了系统代理，而代理不可用 | 确认 `notify.no_proxy` 为 `true`（默认即是） |
| `❌ 推送失败`，连接超时 | 公司网络必须走代理 | 把 `notify.no_proxy` 设 `false`，并用 `notify.proxy` 指定代理地址 |
| 返回成功但**收不到** | 用错了 `notify.type`（报文格式不匹配） | 对照本文表格改 type |
| 返回成功但收不到 | 密钥/地址过期、机器人被移出群 | 重新生成地址 |
| 钉钉返回错误 | 未设「自定义关键词」 | 在钉钉机器人安全设置里加关键词 |
| 微信收不到 | 没关注对应的服务号 | 关注 Server酱 / PushPlus 的公众号 |

## 九、代理陷阱（本机实测踩到过）

很多开发机设了全局 `http_proxy`（指向 Charles / Fiddler 这类调试代理）。
Python 的 `urllib` **会自动读取这个环境变量**，于是代理一关，推送和监测**一起静默失败** ——
而且看起来像「场馆接口挂了」，排查方向会跑偏。

因此本 skill 的配置默认 **直连**：

```json
"request": { "no_proxy": true },
"notify":  { "no_proxy": true }
```

验证直连是否生效：把代理指向一个死端口再跑 `check`，若仍能取到数据，说明没走代理。

```bash
# bash
http_proxy=http://127.0.0.1:1 https_proxy=http://127.0.0.1:1 \
  python scripts/venue_monitor.py check -v example-venue
```

命令行排查时对应 `--no-proxy` 开关。
